요약. 인스턴스별 할 일 박스(todoBoxes = { iid: Todo[] }) 전환은 메인 단일 신뢰 경계에서 (a) 박스 키 형식(IID_RE), (b) 배치된 위젯 iid 격리 검증 (isPlacedTodoBox → NOT_FOUND), (c) todo id 형식(TODO_ID_RE), (d) 텍스트 sanitize·개수 상한을 4채널·에이전트·레거시 흡수 경로 전부에 빠짐없이 적용한다. XSS(L-1)는 렌더가 textContent만 쓰고 innerHTML 유입 0으로 유지된다. 0600 원자적 쓰기·상승 세션 no-op 규약도 보존됐다. 치명·높음 없음 → 보안 게이트 통과. 발견된 보통 2건은 경화(정보 노출 최소화·중앙화) 성격이며 데이터 격리·무결성을 위협하지 않는다.

2 · 보안 불변식 유지 판정

불변식 (CLAUDE.md 마커)판정근거
L-1 · 렌더는 textContent만, innerHTML 유입 0유지 todo text는 el('div',{text:t.text})·aria-label:'완료: '+t.text로만 삽입. el()은 node.textContent=opts.text. 렌더 경로 innerHTML 0.
정규화가 유일 검증 경계(렌더러 입력 전부 불신)유지 normalizeTodoBoxes/핸들러가 box·id·text·dueAt·상한을 강제. 렌더러 applyTodoBoxes는 형식 방어만(권위 아님).
id·시각 스탬프는 메인 생성(렌더러 주입 불가)유지 addTodo가 genTodoId()·nowMs()로 id/createdAt 발급. 렌더러가 준 id/createdAt은 신규 항목에 미반영(재적재 시 normalizeTodos 형식 검사).
인스턴스 격리(남의/미배치 박스 차단)유지 4채널 모두 readTodoBox→isPlacedTodoBox 경유. 미배치·타입 불일치 박스는 NOT_FOUND. 저장 시 normalizeTodoBoxes(...,placed)가 고아 박스 제거.
0600 원자적 쓰기 · 상승 세션 no-op유지 write() tmp→fsync→rename→chmod 0600, isElevated()면 디스크 no-op·메모리 반환. 흡수 write 실패는 normalizeState 폴백(유실·오염 없음).
에이전트도 메인 검증 경로 통과유지 agent 도구는 uiStateIpc.addTodo/toggleTodo/removeTodo({box,...})를 호출 — 격리·검증 우회 표면 없음. box는 agentTodoBox가 배치된 첫 todos iid로 해석(임의 문자열 아님).

T-1 · 보통 addTodo 검증 순서로 인한 박스 존재 오라클

위치 electron/ipc/uiState.js · addTodo() (텍스트 sanitize→INVALID_TEXT가 readTodoBox의 BAD_INPUT/NOT_FOUND보다 먼저 실행).

위협 렌더러(또는 침해된 렌더러 컨텍스트)가 유효 텍스트 + 여러 박스 문자열로 addTodo를 던지면 응답 코드가 NOT_FOUND(미배치) vs ok(배치)로 갈려 어떤 iid가 실제 배치된 todos 위젯인지를 열거할 수 있다.

악용 시나리오 XSS/침해 렌더러가 iid 공간(IID_RE = 32자 이하)을 스캔해 배치 토폴로지를 추론. 단, 이 앱은 로컬 단일 사용자이고 iid는 실행·경로 의미가 없어(표시·키 메타) 노출 가치가 낮다. 데이터 읽기/변조로는 이어지지 않는다(격리 게이트가 여전히 차단).

권고 조치 필수 아님(위험 낮음). 경화하려면 박스 형식/격리 검증(readTodoBox)을 텍스트 검증보다 먼저 수행해 미배치 박스는 텍스트와 무관하게 동일 코드(NOT_FOUND)를 반환 — 오라클 표면 제거. md/scratchpad 채널과 순서 일관성도 확보.

T-2 · 보통 박스 폭증 상한의 분산 정의

위치 normalizeTodoBoxes(MAX_TODO_BOXES=48) 와 배치 게이트(MAX_WIDGETS=48, homeWidgets). 정상 흐름에선 박스 키가 배치된 iid로 게이트되어 위젯 수(≤48)에 종속되지만, allowed 미전달 폴백 경로(순서 의존 회피용)에선 MAX_TODO_BOXES만이 유일 상한이다.

위협 손으로 조작한 ui-state.json(또는 allowed 없는 정규화 경로)에서 박스 키를 최대 48개, 각 200항목×500자까지 채워 파일 크기를 부풀릴 수 있다. 다만 read 단계 MAX_UISTATE_BYTES=1MB 상한이 최종 방어선으로 걸려 실질 DoS(디스크 폭주·파싱 폭탄)는 차단된다. 초과 파일은 graceful 기본값으로 폴백.

악용 시나리오 로컬 파일 조작 필요(외부 공격면 아님) + 1MB 게이트로 흡수 → 영향 제한적. 무결성/격리엔 영향 없음.

권고 조치 현행 유지 가능. 문서화 관점에서 "박스 수의 실효 상한 = min(MAX_TODO_BOXES, 배치 위젯 수)이고 최종 방어는 1MB read 상한"임을 주석으로 명시하면 회귀 시 상한 드리프트를 잡기 쉽다.

T-3 · 낮음 에이전트의 "첫 todos 위젯" 암묵 라우팅

위치 electron/ipc/agent.js · agentTodoBox() — 배치 순서상 첫 type==='todos' 인스턴스를 대상 박스로 고정.

위협(변조) 사용자가 할 일 위젯을 여러 개 두면 에이전트가 의도와 다른 박스에 쓸 수 있다(사용자 놀람). 보안 격리 위반은 아니다 — 대상은 항상 배치된 todos 박스이고 메인 검증(격리·상한)을 그대로 통과한다. 임의 박스 지정 표면은 없다.

권고 조치 보안상 조치 불요(UX 이슈). 향후 에이전트에 박스 선택 인자를 추가하더라도 반드시 readTodoBox 게이트를 경유해야 한다(현행 addTodo 경유가 이를 보장).

T-4 · 낮음 dueAt 값 범위 미검증(유한·양수만)

위치 addTodo/setTodoDue 및 normalizeTodos — dueAt은 유한·>0·Math.floor만 강제, 상·하한(예: 합리적 epoch 범위)은 없음.

위협 렌더러가 극단값(예: Number.MAX_SAFE_INTEGER)을 넣어 마감 감시/알림(notify)·정렬 로직에서 표시 이상을 유발할 수 있다. 코드 실행·격리 위반은 없고 표시 안전(textContent).

권고 조치 필수 아님. 마감 감시 로직의 견고성을 위해 dueAt에 상식적 상한(예: 현재+수십 년)을 정규화 경계에서 클램프하는 것을 선택적으로 검토.

4 · 검증 근거(테스트)

  • 박스 격리: addTodo({box:'wNope'})→NOT_FOUND, toggleTodo가 다른 박스 id면 NOT_FOUND (ipc-uistate.test.js: "todo 박스 격리 — 인스턴스 A/B 독립").
  • 박스 형식: box:'../x'→BAD_INPUT (경로 삽입 시도 차단).
  • 고아 박스 자동 정리: removeWidget 후 그 iid의 todoBoxes 제거.
  • 레거시 흡수: 첫 todos 위젯만 흡수, 재호출 멱등(중복 병합 없음), 미배치 시 legacy 무손실 보존.
  • 에이전트: 미배치 시 add_todo가 no_todo_widget로 무해히 거절, 실제 박스 반영 정합.
  • node --test 3개 스위트 140/140 통과(ipc-uistate·uiStateStore·agent).

5 · 확인 필요(사용자 판단)

게이트 차단 항목 없음. T-1·T-2는 경화 권고(선택)이며 현 상태로도 격리·무결성·XSS 불변식이 유지된다. 수용 여부(경화 반영/보류)는 담당 개발자·PM 판단에 위임한다. 코드 수정은 본 검증자가 수행하지 않는다.
